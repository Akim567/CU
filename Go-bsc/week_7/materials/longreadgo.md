# Лекция: Структура проекта и использование сторонних пакетов

## Введение в структуру Go-проектов

Правильная организация проекта — это основа разработки поддерживаемого и масштабируемого кода. Правильная организация проекта помогает разработчикам легко ориентироваться по кодовой базе, снижает когнитивную нагрузку, ускоряет ревью и упрощает онбординг новых людей на проект. Она также поможет различать границы ответственности при использовании пакетов другими разработчиками и поможет им избежать нежелательных зависимостей.

Хорошая организация проекта поможет не только команде разработки, но и команде инфраструктуры: им будет легче написать CI/CD, и всё будет работать прозрачно "без магии". Ну и конечно же такой проект будет радовать глаз своей красотой внутри GitLab `:)`.

### Почему важна структура проекта?

- **Поддерживаемость** — понятная структура позволяет быстро находить нужные файлы и понимать их назначение
- **Масштабируемость** — хорошо организованный проект легко расширяется новой функциональностью
- **Тестирование** — правильное расположение файлов упрощает интеграцию тестов и их запуск
- **Разграничение ответственности** — другим разработчикам понятно что им можно импортировать из вашего проекта как зависимости
- **Командная работа** — структура по общим соглашениям в вашей команде облегчает совместную разработку
- **Сборка и деплой** — хорошую структуру легко совместить с инструментами сборки Go и CI/CD

## Механизмы видимости пакетов и идентификаторов

Прежде чем приступить к разбору структуры проекта Go, важно понимать механизмы видимости в Go: какие пакеты можно импортировать и какие имена внутри пакетов доступны извне.

### Экспортируемые и неэкспортируемые идентификаторы

Как вы уже знаете, в Go экспортируемые идентификаторы определяются регистром **первой буквы**:
- **Экспортируемые** — начинаются с **заглавной** буквы: доступны из других пакетов.
- **Неэкспортируемые** — начинаются со **строчной**: видны только внутри текущего пакета.

Важно, что это правило применяется не только к объявлениям верхнего уровня (`const`, `var`, `type`, `func`), но также к **полям структур** и **методам**:

```go
package auth

import "strings"

type User struct { // Экспортируемый тип — виден другим пакетам
	ID    string  // Экспортируемое поле — видно в других пакетах
	email string  // Неэкспортируемое поле — видно только внутри пакета auth
}

func New(id, email string) *User { // Экспортируемая функция
	return &User{ID: id, email: email}
}

func (u *User) SetEmail(email string) { // Экспортируемый метод
	u.email = email
}

func (u *User) domain() string { // Неэкспортируемый метод
	i := strings.LastIndexByte(u.email, '@')
	if i < 0 {
		return ""
	}
	return u.email[i+1:]
}
```

Внешние пакеты видят только экспортируемые методы и поля структур.

> [!IMPORTANT]
> Замечание: экспорт типа и экспорт полей — разные вещи.
> 
> Если тип неэкспортируемый, например:
> ```go
> type user struct { Name string }
> ```
> Сам тип `user` нельзя использовать извне, даже если поле `Name` — экспортируемое.

### Директория `internal`

В Go можно импортировать любые пакеты, кроме специальных `main`-пакетов (они предназначены только для сборки исполняемых файлов и **не подлежат импорту**). Однако помимо этого также существует отдельный механизм ограничения импорта — это директория с именем `internal`.

Любой пакет, расположенный внутри директории `internal` (в любой вложенности), **запрещён к импорту извне** зоны видимости этого `internal`.
Ими можно пользоваться **только** из кода, который находится в том же модуле **и** внутри родительского каталога (или его подкаталогов), где расположен `internal`.

> [!NOTE]
> **Пример**
> 
> Пакет `.../a/b/c/internal/d/e/f` может быть импортирован только в пакетах внутри дерева директорий `.../a/b/c`. Он не может быть импортирован в `.../a/b/g` или внутри другого модуля.

#### Как различать что стоит класть под `internal`

Под `internal` стоит класть код, который должен быть доступен только вашему приложению. Это как внутренняя кухня ресторана: только повара знают секретные рецепты и могут готовить блюда. Гости не могут зайти на кухню и приготовить еду сами.

Вне `internal` же должен находиться весь остальной код, который могут использовать другие разработчики в своих проектах. Это как меню ресторана: любой гость может прийти и заказать блюдо по рецепту из меню, но не узнает секретные ингредиенты.

## Структура Go-проекта

Важным концептом Go является его минималистичность: простота, читаемость и предсказуемость важнее «универсальных» шаблонов. Важно, чтобы выбранная структура проекта (также именуемая как `layout`) следовала домену, была понятна команде и не мешала инструментам экосистемы.

Вследствие этого в Go нет единого соглашения о том, как именно стоит организовывать свой проект. Однако в сообществе есть несколько устоявшихся паттернов организации кода разной популярности, на которых опираются разработчики: но важно, что «единственно правильного» нет.

Наша задача — познакомиться с несколькими разными популярными паттернами организации кода для расширения кругозора.

### Официальный гайдлайн

Хотя в Go и нет единого официального layout'а, существует официальный гайдлайн по организации кода под названием «Organizing a Go module» (https://go.dev/doc/modules/layout). Это не строгий стандарт, а рекомендации от авторов Go по организации кода внутри модуля.

Документ описывает несколько типовых паттернов, наиболее часто встречаемыми из которых являются:
- [`Basic command`](https://go.dev/doc/modules/layout#basic-command) - минимальный модуль из одного пакета `main` в корне
- [`Server project`](https://go.dev/doc/modules/layout#server-project) - модуль с поддержкой нескольких точек входа и серверной логикой в пакетах под директорией `internal`

Оба эти паттерна вам уже доводилось использовать при решении домашнего задания. Теперь разберём их поподробней.

#### Basic command

Базовая исполняемая программа (CLI-утилита) организуется в зависимости от сложности и объёма кода.
Самый простой вариант - один файл Go, в котором определена `func main`. В программах побольше код можно разделить на несколько файлов, все они объявляют `package main`:

```
project-root-directory/
  go.mod
  auth.go
  auth_test.go
  client.go
  main.go
```

Точку входа обычно по конвенции объявляют в файле `main.go`.

Данный layout применяют для небольших программ, для которых не требуется разделение логики по пакетам. Его вы применяли на первых неделях ДЗ.

#### Server project

Go часто выбирают для реализации серверов. Обычно серверные проекты не экспортируют пакеты для внешнего использования: сервер - это, как правило, самодостаточная исполняемая программа (или несколько). Поэтому в официальном гайде рекомендуют хранить логику сервера под директорией `internal`. Кроме того, поскольку в репозитории часто будет встречаться много директорий с не-Go кодом, удобно держать все точки входа вместе в каталоге `cmd`. Структура Go кода будет выглядить следующим образом:

```
project-root-directory/
  go.mod
  internal/
    auth/
      ...
    metrics/
      ...
    model/
      ...
  cmd/
    api-server/
      main.go
    metrics-analyzer/
      main.go
    ...
  ... остальные директории проекта с не-Go кодом
```

Разберём плюсы такой структуры:
- В данной структуре явно понятно, что нет экспортируемых пакетов Go - четко видно, что Go код написан в директориях `internal/` и `cmd/`. Серверные проекты часто замкнутые и поэтому им не требуется экспортировать пакеты.
- Отдельно выделена директория `cmd/` с точками входа. Удобство этой отдельной директории мы разберём ниже.
- Все остальные директории могут использоваться как угодно - различать Go код они никак не помешают. Например, в корень проекта можно добавить `docker/`, `chart/`, `.gitlab/` и прочее.

В связи со всеми удобствами, которые предоставляет данный layout, на самом деле большинство других layout'ов используют за основу его: они добавляют лишь дополнительные директории со своим смыслом.

##### Удобство выделения отдельной директории `cmd/`
Представим себе следующую структуру директории `cmd/`:

```
cmd/
  api-server/
    main.go
  metrics-analyzer/
    main.go
```

В каждом `main.go` определяется пакет `main` и своя точка входа `func main` — это независимые бинарники, которые:
- не предназначены для импорта (потому что пакет `main` импортировать нельзя)
- содержат минимум логики, вызывают запуск/остановку приложения из других пакетов
- имеют собственные флаги, окружение и жизненный цикл, не мешая друг другу

Для того, чтобы запустить программу по различным точкам входа (или собрать) достаточно написать:

```bash
go run ./cmd/api-server
go build -o bin/metrics ./cmd/metrics-analyzer
```

Это позволяет удобно добавлять новые точки входа, а также облегачает настройку CI для каждой программы.

##### Когда этот layout не применим

Данный layout несмотря на все свои плюсы, не всегда применим в своём чистом виде. Почему так происходит монятно из его названия - он специально заточен для использования в серверных проектах. Есть ситуации, когда стоит отойти от этой схемы, либо видоизменить её.

Первый случай возникает, когда нам требуется экспортировать переиспользуемые пакеты. Т.к. размещение кода под `internal` закрывает возможность импортировать такой код из сторонних модулей, требуется как-то его экспортировать. Для этого часто создают в корне директорию `pkg/`, куда помещают экспортируемые пакеты. Это может выглядить так:

```go
project-root-directory/
  go.mod
  pkg/
    metrics/
      ...
    model/
      ...
  internal/
    auth/
      ...
  cmd/
    api-server/
      main.go
    metrics-analyzer/
      main.go
    ...
  ... остальные директории проекта с не-Go кодом
```

Для примеров ниже возьмем за основу то, что в `go.mod` прописано:
```go
module github.com/someuser/modname
```

Тогда остальные модули смогут импортировать пакеты из директории `pkg/` следующим образом:
```go
import (
    "github.com/someuser/modname/pkg/metrics"
    "github.com/someuser/modname/pkg/model"
)
```

Но лучше всего вынести переиспользуемые пакеты в отдельный репозиторий/модуль. Дело в том, что папка `pkg/` часто превращается в «свалку общих утилит», а также у зависящих модулей могут возникнуть проблемы с версионированием. Для отдельного репозитория/модуля часто используют типовой паттерн [`Multiple packages`](https://go.dev/doc/modules/layout#multiple-packages):

```
project-root-directory/
  go.mod
  modname.go
  modname_test.go
  auth/
    auth.go
    auth_test.go
    token/
      token.go
      token_test.go
  hash/
    hash.go
  internal/
    trace/
      trace.go
```

К тому же остальные модули смогут импортировать пакеты без указания в своём пути директории `pkg/`, что будет выглядить более наглядно:
```go
import (
    "github.com/someuser/modname/metrics"
    "github.com/someuser/modname/model"
)
```

Важно помнить, что модуль не обязательно создается в корне проекта: в проекте может содержаться несколько модулей, поэтому очень часто для общих зависимостей из модулей создают монорепо. Структура у монорепо выглядела бы следующим образом:
```
project-root-directory/
  auth/
    go.mod
    auth.go
    auth_test.go
    token/
      token.go
      token_test.go
  hash/
    go.mod
    hash.go
    hash_test.go
```

Тогда версионирование каждого модуля будет учитываться отдельно, а импортировать пакеты из разных модулей получится так:
```go
import (
    "github.com/someuser/monorepo/auth"
    "github.com/someuser/monorepo/hash"
)
```

### Структура проекта: не стандарт, а соглашение

Как уже было сказано, ключевая мысль по структуре Go-проекта заключается в том, что у Go нет «единственно правильной» структуры проекта. Важно, чтобы команда заранее договорилась о наборе структурных паттернов и последовательно придерживалась их. Универсальные гайды полезны, но как «делать правильно» для вашего проекта вы узнаете на работе: через практику, код-ревью и локальные соглашения.

В Open-Source проектах часто фиксируют соглашения, в том числе по структуре проекта, в файле `CONTRIBUTING.md`. Важно также не бояться эволюционировать структуру по мере роста проекта.

## Go Modules: управление зависимостями

Go Modules — это современная система управления зависимостями, которая делает работу с внешними библиотеками простой и безопасной. Давайте разберемся, как это всё работает.

### Инициализация модуля

Каждый Go-проект начинается с простой команды:

```bash
# Создание нового модуля
go mod init github.com/username/project-name
```

После выполнения этой команды Go создает два важных файла: `go.mod` и `go.sum`.

- **go.mod** — файл описания модуля и зависимостей
- **go.sum** — файл с криптографическими хешами зависимостей

Остановимся подробнее на файле go.mod.

```go
module github.com/username/project-name

go 1.21

require (
    github.com/gin-gonic/gin v1.9.1
    github.com/golang-migrate/migrate/v4 v4.16.2
    github.com/lib/pq v1.10.9
    github.com/spf13/viper v1.16.0
    gorm.io/driver/postgres v1.5.2
    gorm.io/gorm v1.25.4
)

require (
    github.com/bytedance/sonic v1.9.1 // indirect
    github.com/chenzhuoyu/base64x v0.0.0-20221115062448-fe3a3abad311 // indirect
    // ... другие косвенные зависимости
)
```

### Структура файла go.mod

Файл `go.mod` состоит из нескольких секций, каждая из которых выполняет определённую функцию:

#### Секция `module`

Определяет **имя модуля** — уникальный идентификатор проекта в экосистеме Go:

```go
module github.com/username/project-name
```

Go автоматически умеет загружать зависимости напрямую из Git-репозиториев по указанному пути. Это работает благодаря интеграции Go с системами контроля версий:

**Механизм работы с Git-репозиториями:**
```go
module github.com/username/project-name  // Go будет искать репозиторий на github.com
module gitlab.com/company/team/project  // Go будет искать на gitlab.com
module golang.org/x/text                // Go будет искать на golang.org
```

**Как это работает:**
1. Go определяет хостинг-платформу по доменному имени (github.com, gitlab.com и т.д.)
2. Обращается к API платформы для получения информации о репозитории
3. Скачивает указанную версию или коммит
4. Кэширует зависимость локально

**Для публикуемых библиотек** (которые будут использоваться как зависимости):
```go
module github.com/username/my-library  // Публичная библиотека
module company.com/libraries/utils     // Корпоративная библиотека
```

**Для непубликуемых проектов** можно использовать простые имена:
```go
module my-private-app        // Приватное приложение
module internal-dashboard    // Внутренний проект
module company-project       // Название без домена тоже работает
```

**Важные моменты:**
- При использовании доменного имени Go ожидает найти действующий Git-репозиторий
- Для приватных проектов можно использовать любое имя, но рекомендуется указывать домен для будущей совместимости
- Изменение имени модуля потребует обновления всех импортов в проекте

#### Секция `go`

Указывает **минимальную версию Go**, требуемую для сборки проекта:

```go
go 1.21
```

**Назначение:**
- Гарантирует совместимость с используемыми возможностями языка
- Предотвращает сборку на устаревших версиях Go
- Влияет на поведение некоторых инструментов сборки

#### Секция `require`

Перечисляет **прямые и косвенные зависимости** проекта:

```go
require (
    github.com/gin-gonic/gin v1.9.1           // прямая зависимость
    github.com/golang-migrate/migrate/v4 v4.16.2 // прямая зависимость
    github.com/bytedance/sonic v1.9.1 // indirect  // косвенная зависимость
    github.com/chenzhuoyu/base64x v0.0.0-20221115062448-fe3a3abad311 // indirect
)
```

**Прямые зависимости** — пакеты, которые импортируются напрямую в коде проекта:
```go
import "github.com/gin-gonic/gin"  // прямая зависимость
```

**Косвенные зависимости** (`// indirect`) — пакеты, которые требуются прямым зависимостям, но не используются напрямую в коде проекта.

**Почему `// indirect` важно:**
- Позволяет отличать зависимости, которые можно безопасно удалить
- Упрощает управление зависимостями при рефакторинге
- Помогает понять дерево зависимостей проекта

#### Секция `replace`

Иногда случаются ситуации, когда стандартная зависимость нам не подходит. Может быть, вы нашли баг в популярной библиотеке и хотите его исправить, или разрабатываете новую функциональность и тестируете её с локальной версией пакета. На помощь приходит секция `replace`!

Она позволяет подменить любую зависимость на другую версию или даже на локальный файл.

```go
replace github.com/old/package => github.com/new/package v1.2.3
replace github.com/local/package => ../local/package
```

Эта секция особенно полезна в нескольких сценариях:
- Когда вы отлаживаете проблему и хотите использовать локальную версию пакета для быстрого тестирования исправлений
- Если вы создали форк популярной библиотеки и добавили в неё свою функциональность
- Когда нужно временно исправить баг в зависимости, ожидая официального патча от авторов

#### Секция `exclude`

А что если определённая версия зависимости содержит критическую уязвимость или просто "сломана"? Секция `exclude` работает как страж на границе — она говорит Go: "Эту версию загружать не нужно, пропускай!"

```go
exclude github.com/problematic/package v1.5.0
```

Это особенно ценно, когда:
- Вы знаете о конкретной уязвимости в версии v1.5.0 и хотите предотвратить её использование
- Некоторые версии содержат баги, которые ломают вашу сборку
- Вы хотите гарантировать, что команда случайно не использует проблемную версию

### Файл go.sum

Файл `go.sum` содержит **криптографические хеши** всех зависимостей проекта и обеспечивает безопасность и воспроизводимость сборок:

**Структура файла go.sum:**
```
github.com/gin-gonic/gin v1.9.1 h1:4idEAncQnU5cB7BeOkPtxjfCSye0AAm1R0RVIqJ+Jmg=
github.com/gin-gonic/gin v1.9.1/go.mod h1:hPrL7Yrp6KXt5YId3A/Tnip5kqbEAP+KLuI3SUcPTeU=
github.com/bytedance/sonic v1.9.1 h1:6iJ6NqdoxCDr6mbY8h18oSO+cShGSMRGCEo7F2+0Y8=
github.com/bytedance/sonic v1.9.1/go.mod h1:i736AoUSYt75HyZLuJZ0SSRlHkmaJ2Kl9N6Fz5rD3k=
```

**Каждая строка содержит:**
1. **Путь к модулю** — имя пакета
2. **Версия** — конкретная версия или коммит
3. **Хеш** — криптографическая подпись пакета

**Зачем нужен этот файл?**

Представьте, что вы заказываете товары из интернет-магазина. `go.sum` — это как чек с уникальными номерами каждого товара. Когда курьер привозит заказ, вы проверяете, что номера на товарах совпадают с номерами в чеке. Если кто-то пытается подменить товар, вы сразу это заметите!

Файл `go.sum` выполняет три важные функции:

1. **Надёжная защита** — каждый раз при сборке проекта Go проверяет, что скачанные пакеты точно соответствуют хешам в `go.sum`. Если злоумышленник попытается подменить какую-то зависимость на вредоносный код, Go немедленно остановит сборку с ошибкой.

2. **Идеальная воспроизводимость** — все разработчики команды получают абсолютно одинаковые версии всех зависимостей. CI/CD системы собирают проект с теми же зависимостями, что и на вашей машине.

3. **Полная история версий** — `go.sum` хранит хеши не только прямых зависимостей, но и всех косвенных, включая конкретные коммиты. Это позволяет отследить, какие именно версии пакетов использовались в любой момент времени.

**Как он появляется и обновляется?**
Вам не нужно создавать или редактировать этот файл вручную — Go делает это автоматически:
- Когда вы впервые добавляете зависимость командой `go get`
- При обновлении существующих зависимостей
- Во время выполнения `go mod tidy`

**Важный совет:** Всегда включайте `go.sum` в Git! Этот файл — ваша страховка от неожиданностей и гарантия безопасности проекта.

**Пример реального go.sum:**
```
golang.org/x/crypto v0.14.0 h1:wBqGXzWJW6m1XrIKlAH0Hs1JJ7+9KBwnIO8v66Q9cHc=
golang.org/x/crypto v0.14.0/go.mod h1:MVFd36DqK4CsrnJYDkBA3VC4m2GkXAM0PvzMC4iAlQ=
golang.org/x/crypto v0.0.0-20220622213112-05595931fe9d h1:clV8cF8YDVVF2HhcxKqEwKmFJOEh3m0mVJf6w6JOD2E=
golang.org/x/crypto v0.0.0-20220622213112-05595931fe9d/go.mod h1:IxCIyHEi3z6gQSJsP2xlYpH5J4u2iS0D9mBvI3+JbA=
```
Здесь видно, что для пакета `golang.org/x/crypto` есть две версии: стабильная `v0.14.0` и конкретный коммит `v0.0.0-20220622213112-05595931fe9d`.

### Добавление зависимостей

```bash
# Добавление последней версии пакета
go get github.com/gin-gonic/gin

# Добавление конкретной версии
go get github.com/gin-gonic/gin@v1.9.1

# Добавление пакета для тестов
go get github.com/stretchr/testify@latest

# Обновление всех зависимостей
go get -u ./...

# Удаление неиспользуемых зависимостей
go mod tidy
```

### Работа с зависимостями

Теперь, когда мы разобрались с теорией, давайте поговорим о практике — как же управлять всеми этими зависимостями? Go предоставляет несколько удобных команд, которые делают эту работу почти автоматической.

#### Команда `go mod tidy` — наводим порядок

Представьте, что вы делаете генеральную уборку в квартире. Вы убираете всё ненужное, раскладываете нужное по местам и в итоге получаете идеальный порядок. Команда `go mod tidy` делает то же самое, но с зависимостями вашего проекта!

Она умно анализирует все ваши `.go` файлы и автоматически:
- **Находит забытые зависимости** — если вы добавили новый импорт, но забыли обновить `go.mod`, `go mod tidy` добавит недостающий пакет
- **Убирает мусор** — удаляет из `go.mod` все пакеты, которые больше не используются в коде
- **Обновляет документацию** — приводят в порядок файл `go.sum`, добавляя хеши новых зависимостей
- **Сортирует по полочкам** — упорядочивает все зависимости для удобного чтения

Когда же это нужно делать? Лучше всего выработать привычку запускать `go mod tidy` перед каждым коммитом — так ваш `go.mod` всегда будет в идеальном состоянии. Также эта команда незаменима после крупных рефакторингов или переименований пакетов.

#### Команда `go mod download` — готовимся к офлайн-работе

Иногда нужно работать без интернета — в самолёте, в поездке или просто при нестабильном соединении. Команда `go mod download` заранее скачивает все зависимости в специальный кэш Go, после чего вы можете собирать проект полностью офлайн.

Она делает три полезных вещи:
- Скачивает все пакеты из вашего `go.mod` в локальный кэш
- Проверяет, что скачанные пакеты точно соответствуют хешам из `go.sum`
- Делает ваш проект независимым от интернет-соединения

Эта команда особенно полезна в CI/CD системах, Docker-контейнерах или когда вы работаете в корпоративной среде с ограниченным доступом к внешним ресурсам.

#### Команда `go mod vendor` — создаём полную независимость

Директория `vendor/` — это как переносной дом для всех зависимостей вашего проекта. Команда `go mod vendor` копирует все зависимости в папку `vendor/` прямо внутри вашего проекта.

Зачем это может понадобиться?
- В некоторых корпоративных средах с очень строгими требованиями безопасности
- При использовании старых инструментов сборки, которые не умеют работать с Go Modules
- Для создания полностью самодостаточных сборок, которые не зависят от внешних сетей

**Важный совет:** В 2024 году `vendor/` нужен всё реже. Современный Go отлично работает без этой директории, так что используйте `go mod vendor` только если у вас есть конкретные причины — не нужно создавать её "на всякий случай".

#### Дополнительные полезные команды

**Просмотр дерева зависимостей:**
```bash
# Показать дерево зависимостей
go mod graph

# Показать, почему требуется конкретный пакет
go mod why github.com/gin-gonic/gin
```

**Проверка целостности:**
```bash
# Проверить, что зависимости не были изменены
go mod verify
```

**Версионирование:**
```bash
# Показать информацию о модуле
go list -m all

# Показать доступные версии пакета
go list -m -versions github.com/gin-gonic/gin
```
